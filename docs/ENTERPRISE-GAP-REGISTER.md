## Current-scope boundary

The Xero and ServiceM8 ports added for the current update are transport-injected orchestration contracts only. They contain no credentials and make no live calls by themselves. Xero exposes a fixed Items read. ServiceM8 permits approved Material create and update fields, never deletes or deactivates missing records, and never writes quantity-on-hand. Provider authentication, account selection and production enablement remain separate approval and security gates.

The injected approval-ledger interface is not production authentication and must not be supplied by browser or per-run operator input. Before ServiceM8 production enablement, a protected production-owned native composition root must exclusively wire the authoritative immutable approval ledger, provider transport and protected credential boundary. The ledger record must be loaded by proof reference and exactly bind the actor, approval time, immutable preview fingerprint and ordered intent set before any checkpoint or provider access.

The native composition root must also supply a checkpoint store whose saves are atomic, ordered per run and durable before their promises resolve. Immediately before a non-idempotent create, orchestration persists a write-ahead `create-attempted-awaiting-reconciliation` marker bound to the current item and exact idempotency key. A rejected marker save permits no provider call. After a committed marker, restart performs provider reads and reconciliation only; neither the current run nor a resumed run may create again until an authoritative exact read resolves the item. Later outcome or checkpoint persistence failures must not erase that marker. These are adapter acceptance requirements, not claims that a production persistence adapter or native trust boundary is already wired.

## Least-privilege integration guidance

- For Xero, request `accounting.settings.read` for the fixed Items GET reader. Xero's [current scope matrix](https://developer.xero.com/documentation/guides/oauth2/scopes/) lists Items under that GET-only scope and also under `accounting.invoices.read`; do not add the broader invoice-reading scope merely for this port. Confirm the registered app's assigned scope model before connecting an account, and never request an accounting write scope.
- For ServiceM8, use `read_inventory` for material reads and grant `manage_inventory` only when an approved create or update run needs it. ServiceM8's [current authentication scope table](https://developer.servicem8.com/docs/authentication) defines these as read-only and full Materials/MaterialBundles access respectively. Do not request or use authority for quantity-on-hand changes, deletion or deactivation.
- Keep access tokens, refresh tokens and client secrets inside the protected credential boundary. Do not place them in integration models, logs, checkpoints, SQLite records, browser storage, repository files, workflow artefacts or error messages.
- Treat account selection, credential connection and every live write run as separate operator-approved actions. A preview fingerprint, ordered item identities, persisted retry references and durable approval proof must match before the ServiceM8 execution port can begin provider access. Keep creation of authoritative approval records and construction of the privileged ledger outside operator-controlled application inputs.
